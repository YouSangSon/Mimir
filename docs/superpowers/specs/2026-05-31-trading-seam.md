# S5. Mimir Automated Trading — Seam 설계 (미래)

> **스펙 ID**: S5
> **작성일**: 2026-05-31
> **상태**: **미래(설계 seam만). 구현하지 않음.**
> **선행**: [S2 Analysis](2026-05-31-analysis-design.md) · [S4 Historical](2026-05-31-historical-design.md) · [로드맵](../../architecture/roadmap.md)

---

## 1. 목적

이 문서는 **자동매매를 지금 구현하지 않는다.** 대신 S1~S4가 만든 기반 위에 나중에 매매 엔진을 안전하게 끼울 수 있도록 *경계(seam)* 를 명시한다. 실제 구현은 사용자가 (1) 증권사/브로커를 선택하고 (2) 페이퍼 트레이딩 우선·리스크 한도를 확정한 뒤 별도 스펙으로 진행한다.

## 2. 핵심 원칙 — 분석과 실행의 분리

```
[S2/S4 분석]  --(signals 데이터셋, 읽기 전용)-->  [S5 실행 엔진(미래)]
   인사이트/이벤트                                   전략 → 주문 → 체결 → 리스크
```

- 분석 코드(S2/S4)는 **주문 API를 절대 직접 호출하지 않는다.** 오직 구조화된 *시그널*을 발행할 뿐이다.
- 실행 엔진은 시그널을 **읽기 전용**으로 소비한다. 분석 버그가 곧장 주문으로 이어지지 않는다.
- 이 경계 덕분에 페이퍼 트레이딩으로 충분히 검증한 뒤에만 실거래로 승격할 수 있다.

## 3. 시그널 계약 (미래 추가)

S2 인사이트(`insights`)와 S4(`historical`)는 이미 방향성·확신도·근거를 담고 있다. S5는 이를 행동 가능한 시그널로 좁히는 `signals` 데이터셋을 추가한다(동일 envelope 재사용):

```jsonc
{ "source":"mimir_strategy", "dataset":"signals", "market":"US", "symbol":"AAPL",
  "ts":"...", "idempotency_key":"signal:<strategy>:AAPL:<date>",
  "payload": { "action":"buy|sell|hold", "size_hint":0.0..1.0,
    "confidence":0.0..1.0, "rationale":["..."], "source_insights":["insight:AAPL:..."],
    "paper":true } }
```

## 4. 실행 엔진 컴포넌트 (미래)

| 컴포넌트 | 책임 |
|---|---|
| **Strategy** | 시그널 → 목표 포지션. 규칙 기반 우선(예: ⭐≥4 & 방향 일치 시 진입) |
| **Broker (포트)** | 주문/잔고/체결의 추상 인터페이스. 어댑터로 페이퍼·실거래 교체 |
| **Risk** | 포지션 한도·일일 손실 한도·종목당 비중·킬스위치 |
| **Ledger** | 주문·체결·PnL 기록(같은 git-as-DB 또는 별도 저장) |

## 5. 안전 모델 (실거래 전 필수)

- **페이퍼 우선**: 모든 전략은 페이퍼 브로커에서 충분히 검증 후에만 실거래 승격.
- **시크릿 격리**: 브로커 키는 Actions Secrets/`.env`로만. 절대 커밋 금지.
- **킬스위치**: 설정 한 줄로 전체 매매 비활성화.
- **리스크 한도 강제**: 코드가 한도를 어기는 주문을 거부.
- **감사 로그**: 모든 주문/체결을 불변 기록.
- **GitHub Actions는 실거래 실행기로 부적합**(베스트에포트·시크릿 노출면) — 실거래는 신뢰된 상시 환경에서. cron은 신호 생성까지만.

## 7. 착수 조건 (이 문서가 스펙으로 승격되는 시점)
1. 사용자가 브로커를 선택한다.
2. 페이퍼 트레이딩 우선 + 리스크 한도를 확정한다.
3. 그때 별도 brainstorming → spec → plan → 구현 사이클로 S5를 시작한다.

**그 전까지 Mimir는 시그널만 발행하고 주문은 내지 않는다.**
